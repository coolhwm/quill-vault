# MVP 生成性能诊断与脱敏导出说明

> 状态：已实现，待真机体验验收（Issue #25）
> 日期：2026-08-03

## 1. 目的与边界

诊断用于解释录音、文字记录和纪要生成的阶段耗时、重试与恢复行为，判断瓶颈位于 App 编排、网络还是 Provider。诊断只在设备本地保存；不会自动上传，也不会改变录音、文字记录或纪要的内容真相。

用户只能在“设置 → 诊断”中查看事件数量和保留期限，并主动导出 JSON。导出失败时安全拒绝并提示重试，不影响业务链路。

## 2. 关联标识

事件可携带以下由 App 生成的非内容 ID：

- `meeting_id`：会议 UUID；
- `job_id`：纪要任务 UUID；
- `step_id`：稳定的步骤幂等键（只允许 ASCII 字符）；
- `attempt_id`：单次模型请求 UUID。

标题、文字记录、纪要正文、文件名、目录路径和请求内容不得作为关联标识。

## 3. 事件白名单

持久事件只允许有限标量字段：事件时间、事件类型、关联 ID、阶段耗时、HTTP 状态、字节数、重试次数、Retry-After、服务域名、模型名、Provider token 用量，以及 `URLSessionTaskMetrics` 的 DNS/TCP/TLS/请求发送/首字节/响应结束、协议、连接复用和网络约束字段。

事件类型覆盖：请求排队、录音与文字记录开始/完成、后台计划/开始/完成、DNS、TCP、TLS、请求发送、Provider 首字节、流结束、响应完成、解析完成、检查点保存、重试计划和纪要发布完成。

Provider 的 Authorization Header、API Key、请求/响应正文、文字记录、纪要、录音和私人路径没有对应字段，因此不会进入事件模型。模型名、协议和错误码还会经过 ASCII 标识符白名单；导出前会对 JSON 键和值做失败关闭审计。

## 4. 本地环形存储

`GRDBDiagnosticStore` 使用独立的 `diagnostic_event` 表：

- 最长保留 14 天；
- 默认最多 2,000 条，按时间淘汰最旧事件；
- 写入和淘汰失败只丢弃诊断，不阻塞录音、转写或纪要；读取、预览和导出也会先按当前时间执行 14 天淘汰；
- 导出按时间正序排列，预览按当前数量和时间范围汇总。

## 5. 性能归因

每个模型请求同时记录 App 编排事件和 URLSession 指标。评估 App 侧开销时使用：

```text
App attributable overhead
= total wall-clock
  - URLSession task interval
  - explicit Retry-After / backoff
  - system background pause
```

Provider 首字节和流结束单独记录，不能把 Provider 计算时间误判为 App 阻塞。60 分钟文字记录的验收目标为：App 可归因开销不超过 `min(墙钟时间 × 10%, 10 秒)`；非退避请求间隔 P95 不超过 500ms。模型响应超过两分钟仍可接受，前提是上述分段指标能够解释等待位置。

导出包除了原始事件，还包含按关联 ID 聚合的 `performance` 摘要：总墙钟时间、URLSession 等待、显式退避、App 可归因时间、预算及是否达标。这样无需上传正文即可判断慢点是否在 Provider、网络或 App 编排。

## 6. 隐私自动审计

导出前对 JSON 结构执行失败关闭检查：禁止凭据、认证字段、请求/响应正文、文字记录、纪要、录音字段、路径和私有位置标记；普通模型名（例如 `minutes-model`）不因名称包含业务词而被误判。自动测试覆盖字段审计、环形淘汰、时间排序、网络阶段/首字节、token 用量、性能归因和 Provider 关联事件。
