# Quillvault MVP 需求补充规格：纪要质量与可扩展能力

> 状态：ready-for-agent
> 日期：2026-08-04
> 基线：MVP GitHub Spec #10 与既有 MVP 设计文档
> 目标：补充纪要质量、策略化 AI、可恢复生成、国际化与品牌能力，不改变 MVP 的文件主权和可靠性边界

## Problem Statement

当前 MVP 已经具备录音、文字记录、BYOK 纪要生成和会议资产落盘的基本链路，但仍存在影响内测分发和长期迭代的产品问题：

- 纪要生成后仍使用“会议录音”等无意义标题，用户无法快速识别会议主题；
- 纪要质量和结构不稳定，短会议与长会议使用同一种输出方式，内容密度不足时过度展开，长会议又缺乏完整结构；
- 纪要图示有时不生成，用户无法判断是内容不适合还是生成故障；
- 自动生成由开关控制，但文字记录就绪后的状态、队列和处理反馈不够明确，用户容易误以为需要重试文字记录；
- 文字记录存在同音字和上下文纠错问题，只有原始结果时无法在不损失证据的前提下提升可读性；
- BYOK 配置需要填写过多技术字段，厂商、模型和接口信息没有策略化，新增厂商会侵入核心代码；
- Apple 本地模型仍缺少可验证的产品边界，不能在无法测试的情况下成为 MVP 依赖；
- 缺少本地个人统计，用户无法了解会议投入和长期使用趋势；
- 国际化和中文品牌显示尚未形成长期可维护的本地化边界；
- APP 缺少正式的、可替换的品牌图标。

这些问题不能通过在现有 View 中增加条件分支解决。纪要标题、生成模板、图示、文字记录版本、Provider 预设、状态反馈和本地统计必须成为长期工程中的稳定领域能力，同时保持录音和原始会议资产不受 AI 失败影响。

## Solution

在既有 MVP 架构和领域词汇基础上，增加一层可扩展的“内容生成策略”能力，并把本轮需求收敛为以下产品行为：

1. 纪要首次发布和重新生成时，由 AI 根据会议内容生成主题标题；标题独立持久化，不提供手动编辑，标题失败不能阻塞纪要发布。
2. 纪要提示词和输出约束使用独立、可版本化的资源文件，由策略选择器根据文字记录长度和信息密度选择简版、完整结构或后续策略。
3. 纪要图示采用内容驱动方式：整场会议可以有核心观点图，局部流程、时序、分支或关系适合表达时附加多张局部图；图示缺失不阻塞有效纪要正文。
4. 自动生成仍由用户开关控制。开关开启且文字记录、模型均就绪时自动创建可恢复纪要任务；开关关闭时保留“待生成纪要”，由用户手动触发。
5. 文字记录质量优化保留原始版本，优化版本独立存储并可对比查看；首个交付先提供录音结束后的可选优化，同时为后续必做的实时增量优化预留通用底层链路。
6. BYOK 支持策略化厂商预设和完全自定义模式。厂商目录、默认 Base URL、推荐模型和能力说明可扩展，核心工作流只依赖稳定 Provider 边界。
7. Apple 本地模型仅作为可选 Provider；只有模拟器能够稳定验证可用性、选择和生成流程后才进入开发，不阻塞 BYOK。
8. 增加本地“我的”视图，提供会议次数、总时长、本月时长和按每日时长计算的热力图；设置下沉为二级入口。
9. 首版完成简体中文、繁体中文和英文的本地化基础；中文环境统一显示品牌名“墨匣”，内部工程标识仍为 `Quillvault`。
10. 先提供一个无文字、可替换、适配深浅色和小尺寸的“墨匣 + 声波/记录”抽象图标。

本规格是对 MVP Spec #10 的增量补充。录音优先、权威外部目录、文件内容真相、异步可恢复纪要、宽容发布和隐私诊断等原有约束继续有效。

## User Stories

### 纪要标题

1. 作为会议参与者，我希望纪要生成后自动拥有主题标题，以便在历史列表中快速识别会议。
2. 作为会议参与者，我希望标题描述会议主题而不是显示“会议录音”，以便标题具有实际信息价值。
3. 作为会议参与者，我希望标题只表达主题，日期、时间和时长单独展示，以便列表更易扫描。
4. 作为会议参与者，我希望重新生成纪要时标题同步反映新内容，以便标题不会与新纪要脱节。
5. 作为会议参与者，我希望模型无法返回标题时仍能看到可读的回退标题，以便标题故障不阻塞纪要使用。
6. 作为会议参与者，我希望标题生成失败不会破坏录音、文字记录或已存在的纪要，以便内容始终可恢复。
7. 作为内测用户，我希望不同语言环境下标题生成仍遵循当前文字记录语言，以便标题可直接阅读。

### 纪要模板与内容质量

8. 作为会议参与者，我希望短会议得到几句话的重点总结，以便快速了解结果而不阅读冗余结构。
9. 作为会议参与者，我希望长会议得到完整结构化纪要，以便回顾复杂讨论和执行事项。
10. 作为会议参与者，我希望系统根据文字记录长度和信息密度自动选择模板，以便无需理解技术参数。
11. 作为会议参与者，我希望纪要包含清晰的总览，以便先掌握会议主题、背景和结果。
12. 作为会议参与者，我希望长会议包含带时间范围的智能章节，以便从纪要跳回原始录音和文字记录。
13. 作为会议参与者，我希望纪要提取关键决策及其依据，以便区分已确认事项和讨论意见。
14. 作为会议参与者，我希望纪要提取待办、负责人、截止时间和原文依据，以便直接推动后续工作。
15. 作为会议参与者，我希望纪要标出风险和未决问题，以便知道哪些事项仍需要确认。
16. 作为会议参与者，我希望纪要在适合时展示金句或关键原话，以便保留对决策有价值的表达。
17. 作为会议参与者，我希望提示词策略可以持续改进而不需要重写纪要生成流程，以便产品质量可以长期迭代。
18. 作为维护者，我希望每次纪要生成都记录使用的策略版本，以便问题可以复现、比较和回滚。
19. 作为维护者，我希望可新增简版、完整结构和领域专项策略，而不影响已有任务的恢复，以便版本演进安全。
20. 作为用户，我希望模型输出有小缺陷时仍能看到可读正文，并明确提示可能不完整，以便内容质量和可用性平衡。

### 纪要图示

21. 作为会议参与者，我希望整场会议在存在清晰关系时生成核心观点图，以便快速理解整体结构。
22. 作为会议参与者，我希望流程、时序、分支或局部关系适合图示时生成对应局部图，以便图示服务于内容而不是装饰。
23. 作为会议参与者，我希望一份纪要可以包含多张图，以便同时表达全局和局部关系。
24. 作为会议参与者，我希望短会议在没有合理图示内容时可以不生成图，以便避免无意义的图。
25. 作为会议参与者，我希望图示生成失败时正文仍然可读，以便图示故障不会让整份纪要失败。
26. 作为会议参与者，我希望图示缺失有明确提示并可重新生成，以便知道如何获得更完整的纪要。
27. 作为维护者，我希望图示生成结果具有可验证的数据边界，以便不能安全渲染的模型输出被隔离而不影响正文。

### 自动生成与可恢复任务

28. 作为用户，我希望通过设置开关决定文字记录就绪后是否自动生成纪要，以便控制网络、费用和处理时机。
29. 作为开启自动生成的用户，我希望完整文字记录写入后自动进入纪要任务，以便无需重复点击技术性按钮。
30. 作为关闭自动生成的用户，我希望会议保持“待生成纪要”并提供明确的生成入口，以便稍后按需处理。
31. 作为用户，我希望首页突出显示正在生成的纪要及其进度，以便知道会议仍在处理而不是已经失败。
32. 作为用户，我希望生成期间仍能查看文字记录和播放录音，以便不被异步任务阻塞。
33. 作为用户，我希望生成任务进入后台、锁屏、网络波动或 App 退出后仍可继续，以便不会丢失已完成工作。
34. 作为用户，我希望生成失败只暂停任务而不损坏原始资产，以便修复配置或网络后继续。
35. 作为用户，我希望可以手动继续或重新生成，以便在自动恢复不及时或结果不满意时自行处理。
36. 作为用户，我希望重新生成可以使用当前选择的模型，而继续任务仍使用创建时的模型快照，以便结果可解释。
37. 作为用户，我希望同一会议不会同时运行多个生成任务，以便避免竞争写入和重复扣费。
38. 作为用户，我希望录音优先于纪要生成，以便 AI 处理永远不会影响新的原始录音。

### 文字记录质量优化

39. 作为用户，我希望开启文字记录质量优化后，系统根据上下文纠正常见同音字和明显识别错误，以便文字记录更接近真实对话。
40. 作为用户，我希望质量优化提示词不绑定某一种语言，以便未来支持中文、英文和其他语言。
41. 作为用户，我希望原始文字记录永久保留，以便在优化结果有误时回溯证据。
42. 作为用户，我希望能并排或切换查看原始与优化版本，以便判断 AI 做了哪些修改。
43. 作为用户，我希望质量优化失败时仍能使用原始文字记录生成纪要，以便优化不是不可逆前置条件。
44. 作为维护者，我希望文字记录版本、优化来源和上下文范围可追踪，以便未来支持增量优化和问题诊断。
45. 作为用户，我希望未来可以在录音过程中获得实时质量优化，以便尽早看到更可读的文字记录。
46. 作为维护者，我希望当前架构已经预留实时增量处理、有限上下文和版本关联，以便后续实现实时优化时不重写录音与转写链路。

### BYOK 与模型 Provider

47. 作为普通用户，我希望选择常用 AI 厂商后只需填写 Key，以便减少 Base URL 和模型字段的配置负担。
48. 作为高级用户，我希望可以选择完全自定义模式并自行填写完整接口地址、模型和参数，以便接入自建或小众服务。
49. 作为用户，我希望厂商预设自动提供合理的 Base URL、推荐模型和流式能力提示，以便减少输入错误。
50. 作为用户，我希望仍可修改预设带出的字段，以便适配厂商的代理、网关和兼容接口。
51. 作为维护者，我希望新增厂商只需增加策略资源或目录条目，不需要改动核心生成工作流，以便 Provider 生态持续扩展。
52. 作为用户，我希望连接测试是真实的模型能力测试，而不是只检查 URL 或 HTTP 状态，以便保存后预期可靠。
53. 作为用户，我希望多个模型配置可以同时保存并切换当前生效模型，以便按会议场景选择能力和成本。
54. 作为用户，我希望 API Key 继续只保存在设备 Keychain 中，以便预设和诊断不会泄露密钥。

### Apple 本地模型

55. 作为支持 Apple Intelligence 的用户，我希望在本地模型可验证时看到它作为可选模型，以便在合适场景下使用设备能力。
56. 作为 BYOK 用户，我希望 Apple 本地模型不可用时仍能正常使用 BYOK，以便本地能力不是单点故障。
57. 作为维护者，我希望只有模拟器能够稳定验证本地模型选择和生成后才实现该能力，以便不把无法验收的路径交付给内测用户。

### 个人视图与统计

58. 作为用户，我希望在底部“我的”视图看到会议总次数，以便了解自己的使用频率。
59. 作为用户，我希望看到会议总时长和本月时长，以便了解投入规模。
60. 作为用户，我希望用类似 GitHub 的每日热力图查看会议时长分布，以便发现使用规律。
61. 作为用户，我希望统计完全基于本地会议资产，不上传到服务端，以便保持隐私。
62. 作为用户，我希望从“我的”进入设置，以便底部导航只保留核心工作入口。
63. 作为用户，我希望会议资产被外部修改或索引重建后统计仍能恢复，以便统计不依赖不可重建数据库。

### 国际化与品牌

64. 作为简体中文用户，我希望首页和所有功能界面将产品显示为“墨匣”，以便品牌表达统一。
65. 作为繁体中文用户，我希望看到繁体本地化界面和同样的“墨匣”品牌，以便中文体验一致。
66. 作为英文用户，我希望看到英文界面和 `Quillvault` 品牌，以便不被中文文案干扰。
67. 作为维护者，我希望新增语言只需要增加本地化资源而不改业务代码，以便持续扩展语言。
68. 作为用户，我希望状态、错误、权限和诊断反馈都参与本地化，以便关键流程不会混杂语言。

### APP 图标

69. 作为用户，我希望看到清晰、简洁且有记录感的 APP 图标，以便在主屏幕快速识别墨匣。
70. 作为用户，我希望图标在深色、浅色和小尺寸下仍然清楚，以便系统主题变化不会降低辨识度。
71. 作为品牌维护者，我希望图标不嵌入文字且可替换，以便后续视觉升级不会影响功能实现。

## Implementation Decisions

### 1. 基线与模块边界

- 本规格是对 MVP Spec #10 的增量，不复用 Demo 工程结构，不把 Demo 渐进改造成正式产品。
- 继续使用 iOS 26、Swift 6、SwiftUI、Observation、Swift Concurrency、本地 Swift Packages、GRDB 和现有 Domain → Application → Infrastructure 边界。
- 录音、文字记录、纪要、模型配置、目录授权和诊断仍通过 Application 用例编排，Feature 只投影状态并处理用户动作。
- 主要扩展点放在 Application 的策略和 Provider 边界，不在 View 中加入提示词、厂商判断或生成重试。

### 2. 纪要标题

- 增加独立的 `纪要标题` 领域字段和索引字段，与会议目录名、日期、录音文件名分离。
- 首次生成和重新生成都由当前纪要内容生成主题标题；MVP 不提供用户编辑标题功能。
- 标题只表达主题，日期、时间和时长作为独立元数据展示。
- 模型标题缺失、过长、空白或不可读时，使用确定性回退标题；标题生成不能让正文发布失败。
- 重新生成产生新标题；若新标题无效，保留上一次有效标题。

### 3. 纪要生成策略与提示词资源

- 提示词、输出约束、段落结构、策略标识和策略版本放在独立资源中，由策略加载器提供给 Application。
- 资源必须可版本化、可测试、可替换；业务流程只依赖策略接口，不依赖具体文本。
- 策略选择器基于文字记录长度、时间跨度、段落数量、信息密度和可识别主题复杂度选择输出层级。
- 短会议策略输出简洁总结和关键事项；长会议策略输出总览、智能章节、关键决策、待办、风险/未决问题、金句和适合的图示；中等会议按内容取舍。
- 从提供的飞书妙记样例反向蒸馏的结构作为长会议策略的参考契约：主题标题、AI 生成提示、总结总览、嵌套主题、章节时间点、待办、关键决策/问题/依据、金句和图示。
- 不复制样例中的业务内容或私有数据；只保留可泛化的结构、信息层次和质量要求。
- 任务快照必须记录策略 ID/版本和输入内容版本，保证恢复、比较和问题复现。

### 4. 图示

- 保留核心观点图和局部图两个语义层级，但局部图数量由内容决定，不限制为单图。
- 模型可返回结构化关系，App 负责安全规范化和确定性 Mermaid 生成；不接受未经验证的任意资源引用。
- 图示是可选输出字段。适合图示的内容应尝试生成，不适合或生成失败时发布正文并提示信息可能不完整。
- 图示渲染继续使用离线、固定版本的 Mermaid 资源，渲染失败不能回滚有效正文。

### 5. 自动生成与任务状态

- 自动生成开关是用户设置，不是无条件强制行为。
- 开关开启、文字记录已就绪且存在可用模型时，Application 自动创建可恢复纪要任务；开关关闭时保持待生成纪要。
- 首页和详情页展示纪要生成中、阶段、百分比和恢复入口；不再用“重试文字记录”表达纪要待处理状态。
- 继续任务沿用原文字记录版本、策略快照和模型配置快照；重新生成创建新一代任务。
- 继续使用既有检查点、原子写入、旧纪要保护、录音优先和“失败不等于会议终态”约束。

### 6. 文字记录质量优化

- 原始文字记录是不可变证据；优化结果是独立的文字记录版本，并带有来源版本、策略版本和处理时间。
- MVP 首个交付提供录音结束后的可选优化，优化结果可预览、对比和作为纪要输入。
- 默认语言无关的优化策略只描述纠错、上下文一致性和不确定性保留，不绑定中文规则。
- 优化失败保留原始文字记录，用户仍可生成纪要。
- 架构预留增量优化端口：可以接收连续文字记录片段、有限上下文和版本关系，不阻塞录音写入，不覆盖原始结果；实时优化是后续必做能力。

### 7. BYOK Provider 目录

- 保留统一的 OpenAI-compatible Provider 边界和现有模型配置快照机制。
- 增加策略化厂商目录：厂商显示名、标识、默认 Base URL、推荐模型、能力标签、流式支持和配置提示均为资源数据。
- 选择预设厂商时简化输入；选择自定义时保留当前完整字段能力。
- 用户填写的 Base URL 视为完整接口地址，App 不校验固定后缀、不拼接路径，避免破坏自定义网关。
- Provider 目录新增或变更不能改变核心 Application 工作流，也不允许把 API Key 放入资源文件或诊断。
- 连接测试继续发送真实的最小请求并验证代表性模型响应。

### 8. Apple 本地模型闸门

- 抽象为可选模型 Provider，不能让核心纪要工作流依赖 BYOK 或设备端某一种实现。
- 只有模拟器可稳定执行模型检测、选择、生成、失败和重试验证后才进入开发；未通过则保持 BYOK 路径并延期。
- 本规格不把本地模型作为 MVP 发布阻塞项。

### 9. 个人视图与统计

- 新增“我的”一级 Feature；底部主导航形成首页、纪要、我的三个入口。
- 设置作为“我的”的二级导航，不改变模型配置、目录授权和诊断的领域边界。
- 统计从会议资产和可重建索引派生，至少支持总次数、总时长、本月时长和每日时长热力图。
- 统计不上传、不引入账号或云端画像；索引丢失时可以从权威目录重建。

### 10. 国际化与品牌资源

- 所有用户可见字符串使用本地化资源，不在 View 或 Domain 中硬编码文案。
- 首版资源覆盖简体中文、繁体中文和英文；中文环境的产品品牌统一为“墨匣”，英文保留 `Quillvault`。
- 工程名、Bundle ID、文件格式、领域字段和外部目录结构继续使用 `Quillvault`，不因语言改变。

### 11. APP 图标

- 增加首版无文字纯图形图标，抽象墨匣和声波/记录意象。
- 图标资源必须提供主屏小尺寸、浅色和深色表现；后续品牌升级可以替换资源而无需变更业务代码。

### 12. 主要测试 seam

- 以 Application workflow boundary 作为本规格唯一主行为 seam。
- 通过注入文件存储、模型 Provider、提示词策略、厂商目录、诊断、时间和随机性适配器，驱动用户命令并断言公开状态、持久检查点、版本关系和权威资产。
- Feature 层只补充必要的状态投影、导航、本地化和可访问性验证；平台能力使用适配器集成测试及真机/模拟器验收，不在 View 内复制业务逻辑。

## Testing Decisions

### 测试原则

- 测试外部可观察行为，不测试私有方法、SwiftUI 布局实现、GRDB SQL 细节或 Actor 调度细节。
- 每个测试应能说明用户看到的状态、生成的文件、版本关系、Provider 请求或安全边界。
- 任何 AI 输出测试都使用脱敏、确定性的模型 Stub/Fixture，不依赖真实模型质量；真实 BYOK 只在真机验收使用。

### 核心应用用例测试

- 延续现有 `GenerationWorkflowTests`、`HomeRecordingModelTests`、`MeetingDetailModelTests` 和模型配置工作流测试的注入式形状。
- 验证标题生成、标题回退、重新生成标题更新和正文发布解耦。
- 验证策略选择器对短、中、长及低信息密度文字记录的外部输出差异，并确认策略版本进入任务快照。
- 验证一张核心图、多张局部图、无适合图示、非法图示和图示生成失败时的正文发布行为。
- 验证自动生成开关开/关、文字记录未就绪、模型不可用、后台恢复和手动生成的状态反馈。
- 验证原始/优化文字记录版本、对比读取、优化失败回退和纪要输入版本绑定。
- 验证 Provider 预设、自定义模式、目录新增、字段覆盖和真实连接测试的公开结果。
- 验证模型配置快照、策略快照和文字记录版本在继续/重新生成之间的隔离。
- 验证统计从资产重建、跨月计算、热力图强度和无资产初始状态。

### 基础设施与集成测试

- 验证提示词资源和厂商目录的版本、缺失资源、非法配置和回退策略。
- 验证 YAML/Markdown 标题字段、索引同步、外部修改、数据库重建和旧资产读取。
- 验证 Keychain 访问、凭据不进入目录/诊断、完整 Base URL 不被拼接或偷偷修正。
- 验证 Mermaid 离线渲染、多图文档、不可渲染图示隔离和无远程资源访问。
- 验证本地化资源在简中、繁中和英文下的品牌名、状态、错误、无障碍标签和动态文本。
- 验证动态字体、VoiceOver、减少动态效果、浅色/深色和图示回退；不以像素细节作为唯一断言。

### 平台与验收

- 真机验证长时间录音、后台/锁屏、音频中断、录音优先、文字记录补齐和冷启动恢复。
- 真机验证纪要生成的后台、网络中断、强杀、重启、模型错误、图示缺失和重新生成。
- 真机验证 Action Button 使用与首页同一录音用例，不能覆盖中断会议。
- 模拟器验证 Apple 本地模型的检测、选择和生成路径；模拟器不通过时不进入该能力开发。
- TestFlight 验证新的“我的”入口、中文品牌、三种语言资源、首版图标和长文本可读性。
- 使用 Feishu 结构脱敏样例和短/中/长文字记录作为回归 Fixture，不把源文档中的私有业务内容纳入测试数据。

## Out of Scope

- 用户手动编辑纪要标题；标题只由生成策略提供，失败使用回退标题。
- 用户每次手动选择纪要模板；模板由策略选择器根据内容自动选择。
- 本规格首个交付中完整实现录音过程实时质量优化；但实时优化是必做后续能力，当前架构验收必须保留通用增量处理 seam。
- 在模拟器无法稳定验证前交付 Apple 本地模型生成纪要；BYOK 仍是 MVP 纪要路径。
- 非 OpenAI-compatible 专有协议、服务端代理、账号体系、云端统计、团队协作或自动上传诊断。
- 说话人分离、声纹识别、视频/系统音频录制、批量导入、完整内容编辑器和语义搜索。
- 依赖第三方通用 UI 框架替代现有 Design System；AI 生成的装饰素材不承担关键状态表达。
- 在本规格中重新设计权威目录、录音优先、文件内容真相、GRDB 可重建索引或可恢复纪要任务的既有约束。
