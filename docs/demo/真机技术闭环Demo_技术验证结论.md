## 结论摘要

Quillvault 的核心产品假设已在 iOS 26 真机上完成端到端技术验证：

1. iPhone 可以持续记录一场长时间中文面对面会话；
2. App 进入后台或锁屏后，原始录音仍可持续写入；
3. 设备端转写能够产出带音频时间范围的完整逐字稿；
4. DeepSeek BYOK 能够只使用逐字稿文本生成结构化纪要；
5. App 能够在本地校验并修复可恢复的模型格式偏差；
6. 结构化图数据能够确定性生成 Mermaid `flowchart`，使用本地资源离线渲染、编辑并重新渲染；
7. `recording.m4a`、`transcript.md` 和 `minutes.md` 能够写入用户选择的同一权威目录；
8. Keychain 中的 BYOK 配置与安全书签保存的权威目录授权能够在冷启动后继续使用；
9. 下游失败不会删除录音和逐字稿，也不会留下残缺的权威 `minutes.md`。

因此，`真机技术闭环 Demo` 所承担的技术可行性验证目标已经完成。该结果证明路线可行，但不表示当前原型已经具备生产质量。

## 逐项验收结果

### 1. 真机长时间录音与后台记录

**结果：通过。**

- 会话时长显著超过 Demo 要求的 15 分钟；
- 后台或锁屏时长显著超过 Demo 要求的 5 分钟；
- 最终录音文件持续 3458.6 秒；
- 文件包含有效 AAC 音频包，未发现已知音频丢失；
- 后台期间不要求实时字幕持续刷新，录音生存优先。

### 2. 设备端逐字稿

**结果：通过。**

- 逐字稿保留音频时间范围；
- 最终产生 241 个片段；
- 时间轴延伸至录音末尾；
- volatile 与 final 结果在 UI 中可区分；
- 前后台切换后仍能继续产生后续转写结果；
- 无已知重复片段或有人声但无字幕的空洞。

### 3. DeepSeek BYOK

**结果：通过。**

- API Key 仅保存于 Keychain，界面不回显完整密钥；
- Base URL 和 Model 可持久化；
-“保存并测试”执行真实模型请求并校验代表性结构字段；
- 纪要请求仅包含逐字稿文本，不包含录音载荷或本地音频 URL；
- 57 分钟逐字稿完成 6 段摘要及最终合并；
- 最终输出包含总览、摘要、章节、决策、行动项、风险、未决问题和核心观点图。

模型偶尔会返回轻微越界的舍入时间、缺失的次要字段、空图节点或不可用链接。验证器采用“可恢复则本地规范化，不可恢复才拒绝”的边界：

- 时间范围截断至真实逐字稿边界；
- 缺失的展示字段使用已有核心文本生成安全默认值；
- 丢弃悬空 Mermaid 边；
- 本地生成受控图节点；
- 来源链接固定为会议资产目录内的相对链接；
- 空内容、非法 JSON 或完全缺少核心文本仍然失败。

该策略保证模型格式波动不会阻止有效摘要展示，同时保留不可恢复输出的失败边界。

### 4. Mermaid

**结果：通过。**

- 模型只返回受约束的节点和边；
- App 确定性生成 `flowchart TD`；
- Mermaid 运行时来自 App 本地资源；
- 真机可离线渲染；
- 用户确认编辑 Mermaid 源码并点击重新渲染后，图形成功更新且无报错；
- 无远程脚本或 Mermaid 业务网络请求。

### 5. 权威目录与会议资产

**结果：通过。**

同一会议目录内存在：

```text
meeting-20260729-142439/
├── recording.m4a
├── transcript.md
└── minutes.md
```

`minutes.md` 包含 YAML Front Matter、结构化纪要、Mermaid 源码和以下相对链接：

```markdown
[transcript.md](./transcript.md)
[recording.m4a](./recording.m4a)
```

Markdown 文件是内容真相，没有引入私有会议内容数据库或隐藏镜像副本。

### 6. 冷启动恢复

**结果：通过。**

用户冷启动 App 后确认：

- BYOK 配置仍然存在；
- Keychain 中保存的 API Key 仍可使用；
- 权威目录书签恢复成功；
- 无需重新选择目录即可开始录音并继续写入。

### 7. 故障安全

**结果：通过。**

真机和自动化测试均覆盖下游失败：

- 转写失败时保留原始录音；
- BYOK 超时、非法 JSON、无效业务结构或重试耗尽时保留录音和逐字稿；
- Mermaid 渲染失败时保留源数据；
- 文件写入失败不报告成功；
- 失败不会留下残缺的 `minutes.md`；
- 用户可以基于已完成的 `transcript.md` 重新生成纪要，无需重复录音或转写。

## 非阻塞问题与后续打磨

以下问题不改变本次技术可行性结论，但进入正式产品开发前应重新设计或优化：

1. **长纪要生成耗时**
   `deepseek-v4-pro` 默认 thinking、完整结构化分段输出和串行合并会放大耗时。可通过关闭非必要 thinking、按文本量而非固定时长分块、轻量中间摘要和请求耗时指标优化。

2. **纪要内容质量**
   模型可能把已经完成的历史动作误判为行动项。正式产品应强化“未完成后续任务”的行动项定义，并继续提高证据约束。

3. **完整结构展示**
   Demo UI 重点展示核心结果，没有为章节、决策、风险和全部行动项提供正式产品级浏览体验。

4. **生产可靠性**
   本次只证明约定真机场景可行，不覆盖进程被系统终止、跨设备文件冲突、生产级文件协调、崩溃恢复、长周期兼容性和 App Store 发布质量。

5. **原型不可直接产品化**
   当前代码为抛弃式可行性原型。正式产品需要重新评估模块边界、状态恢复、错误模型、性能、可访问性、安全审计和测试策略，不应默认沿用 Demo 架构。

## 与 ADR 0001 的边界

[ADR 0001](../adr/0001-ios26与双纪要模式.md) 定义了更完整的 v1 技术可行性闸门，其中包括 Action Button、设备端纪要方向和精确的 60 分钟验证目标。

本次 Demo 明确缩小了范围：

- BYOK 是唯一纪要生成验收路径；
- Action Button 不在 Demo 范围；
- 设备端纪要不作为通过条件；
- Demo 的正式门槛是至少 15 分钟会话和至少 5 分钟后台/锁屏。

因此，本报告支持的结论是：

> Quillvault 真机技术闭环 Demo 已通过，核心技术路线可行，可以进入下一阶段产品决策或正式工程设计。

本报告不单独宣称 ADR 0001 中完整 v1 技术闸门的所有扩展条件已经完成。
